# 《荒天纪》全工程代码审查报告 v1.0

> 审查对象：`cultivation-game`（FastAPI 后端 + 原生 JS 前端 + YAML 内容层）
> 审查基线：`main` 分支，提交 `8bf15a1`；`pytest backend/tests -q` → **129 passed**
> 审查方式：全量阅读核心链路 + 跨层引用核对 + 可执行用例复现（见附录 A）
> 审查范围：核心循环与状态管理、初始化与资源加载、输入处理、角色与实体行为、战斗判定、场景/区域/禁地切换、计分与进度结算、持久化、异常边界、模块依赖。

---

## 0. 结论摘要（TL;DR）

| 维度 | 结论 |
|---|---|
| 架构分层 | 良好：`web → api → services → domain/content → core/db`，`domain` 不依赖 DB/FastAPI |
| 测试 | 良好：129 项回归全绿，覆盖 API/领域/服务/Web 冒烟 |
| 安全基线 | 良好：Pydantic `extra="forbid"`、SQL 全参数化、前端 `textContent`、存档 HMAC、RNG 不落前端 |
| 主要风险 | **集中在"跨仓储事务边界"与"结算顺序"**：存在 2 处 P0（资损/重复发奖）、7 处 P1（核心数值与状态机缺陷） |
| 上线建议 | **不建议直接长期开档**。先修 P0 + P1，再补事务与边界回归测试 |

**最严重的 5 个问题（先看这里）**

1. **兑换先扣贡献、后校验境界/物品** → 玩家贡献被扣但拿不到东西（P0）。
2. **发奖幂等日志最后才写** → 中途失败（如背包满）后重试会**重复发奖**（P0）。
3. **一次业务跨多个独立提交** → 版本冲突/异常时出现"物品没了、角色没加"的半写状态（P1）。
4. **`exp_overflow` 永不回流** → 溢出修为永久沉积，升级进度丢失（P1，已复现）。
5. **突破根基次数跨境界累积** + **根基加成恒为 0** → 根基永久劣化且设计中的成功率加成从未生效（P1）。

| 级别 | 含义 | 处理要求 |

## 2. 问题清单

### 2.1 P0（立即修复）

#### P0-1 兑换先扣费、后校验，失败即资损
- **位置**：`backend/app/services/sect_bridge_service.py:361-392`；扣费在 `backend/app/services/exchange_service.py:164-227`
- **成因**：`ExchangeService.check_and_exchange()` 在独立事务里先扣贡献并写兑换日志；返回后 `sect_bridge_service.exchange()` 才做境界校验（`:373-374`）与内容存在性校验（`:370-372`、`:379-381`、`:388-390`）。任一校验失败直接抛错，但扣费已提交。
- **影响**：兑换高于当前境界的功法、或内容 id 配错时，**贡献点被扣、物品未发放**。可稳定复现，属直接资损。
- **修复建议**：
  1. 把所有可失败校验（境界、内容存在、背包容量、宗门归属）**全部前移到扣费之前**；
  2. 更彻底：将"校验 → 扣费 → 发放 → 写兑换日志"收敛为**同一事务**，任一步失败整体回滚（需先解决 P1-1 的事务边界问题）。
- **回归用例**：`境界不足兑换 → 贡献不变`、`内容不存在 → 贡献不变`、`正常兑换 → 扣费且到账`。

#### P0-2 发奖幂等日志写入过晚，部分失败会重复发奖
- **位置**：`backend/app/services/grant_service.py:117-179`（`GrantLogRepository.record` 在 `:178`，所有副作用在此之前）
- **成因**：`grant()` 先执行修为/灵石/属性/物品/装备/功法等写入，最后才写 `reward_grant_log`。若第 N 个物品触发背包满（`:127-129`）或内容缺失（`:124`、`:136`、`:147`）抛错，前面的写入已各自提交，幂等键却没落库。
- **影响**：调用方重试（战斗中重开、任务重复领取、禁地重结算）时 `exists()` 查不到记录 → **同一奖励发两次甚至多次**，经济系统失真。
- **修复建议**：
  1. 先做**全部可失败预检**（内容存在、境界、背包容量、道具数量），再执行写入；
  2. 幂等占位与副作用放在**同一事务**（先 `record` 占位，失败回滚）；
  3. `GrantLogRepository.record()` 返回 `False` 时必须回滚/返回 duplicate，不能继续当成功。
- **回归用例**：背包满时发多物品奖励 → 抛 4015 且**无任何副作用**；重试不重复。

### 2.2 P1（高）

#### P1-1 事务边界不统一：一次业务 = 多次独立提交
- **位置**：`backend/app/db/repository.py:141-156`（`transaction()` 每次退出即 `commit`）；典型跨仓储序列：`progress_service.py:95-100`（先 `TechniqueRepository.upsert` 再 `CharacterRepository.update`）、`progress_service.py:271-273`、`287-290`、`335-345`、`main_quest_service.py:135-149`、`sect_bridge_service.py:256-281`
- **成因**：`game_repository.py` 的每个方法各自 `with transaction()` 提交；部分旧 `repository.py` 方法（如 `SectMemberRepository.upsert:181-208`）又**不自带提交**、依赖调用方。两层混用导致提交点不可预测。
- **影响**：角色 `update` 触发乐观锁 4004 时，先前的功法/背包/贡献变更已经提交 → **半写状态**；读档 `restore_snapshot` 逐表提交，中途失败会留下"部分恢复"的角色。
- **修复建议**：引入统一事务上下文（`UnitOfWork`）：`transaction()` 支持嵌套 `SAVEPOINT`、仅最外层 commit；Repository 接受外部 `conn`；服务层一个业务入口只开一次事务。
- **回归用例**：注入版本冲突，断言所有子表均回滚。

#### P1-2 `exp_overflow` 永不回流，溢出修为丢失
- **位置**：`backend/app/domain/level.py:113`（`pool = cultivation + gain`，未加 `exp_overflow`）
- **成因**：`exp_overflow` 只在返回值里累加（`:140`），从不参与升级池计算。
- **复现**（附录 A）：`apply_exp(1, 0, 5000, 0, ...)` → `level=1, cultivation=0, exp_overflow=5000`；同样 5000 作为 `gain` → 直升 `Lv.6`。
- **影响**：连升上限/封顶产生的溢出修为**永久作废**，玩家实际成长慢于设计；`action_service.py:299-301`、`grant_service.py:71-73`、`story_event_service.py:109-111`、`progress_service.py:241-243` 四处结算全部受影响。
- **修复建议**：`pool = cultivation + exp_overflow + gain`，结算后把已消费的溢出清零；补"溢出→下次立即续升"的单测。

#### P1-3 `realm_attempts` 从不清零，根基跨境界劣化
- **位置**：`backend/app/services/breakthrough_service.py:134`（`attempts = realm_attempts + 1`）、`:142-163`（成功分支未写 `realm_attempts: 0`）
- **成因**：`game.sql:48` 明确该字段是"**本境**突破尝试次数"，但成功突破后未重置。
- **影响**：第二境起 `attempts` 继承上一境总次数，`foundation_of()`（`domain/realm.py:213-237`）很快落入"虚浮/崩坏"，玩家被**永久扣属性**（-300/-800 bp），且越后期越不可逆。
- **修复建议**：成功时 `fields["realm_attempts"] = 0`；根基判定改用本境次数；补"连续两境首次突破均为圆满"的用例。

#### P1-4 根基加成从未参与突破成功率（`foundation_bp` 恒 0）
- **位置**：`backend/app/services/breakthrough_service.py:87`、`:126`（均传 `foundation_bp=0`）；`domain/realm.py:240-242` 的 `foundation_bp()` 无调用方
- **成因**：设计公式为"基础 + 体质 + **根基** + 准备 + 连败补偿"，但实现把根基固定为 0。
- **影响**：`preview` 的"根基"一项永远显示 0；根基对成功率完全无效，只影响属性加成，设计意图落空。
- **修复建议**：明确口径（建议用**上一境根基**的 `next_realm_bp`，或本境累计的 `foundation_bp(attempts)`），`preview` 与 `execute` 使用同一入参。

#### P1-5 写接口缺少"待决事件 / 战斗进行中"互斥守卫
- **位置**：仅 `action_service.py:273-277` 有守卫；以下入口均无：`progress_service.py:78-101`（学功法）、`106-137`（参悟）、`140-175`（装备）、`222-275`（用物品）、`278-292`（出售）、`318-348`（强化）、`378-396`（传送）、`breakthrough_service.py:111`、`sect_bridge_service.py:223/311/345/397/485`
- **成因**：守卫逻辑散落在个别服务，未收敛为公共前置。
- **影响**：玩家可在**事件待决或战斗进行中**吃丹药、学功法、传送改区域、甚至突破，绕过状态机；战斗会话/事件上下文与角色状态可能不一致。
- **修复建议**：在 `services/context.py` 增加 `assert_idle()`（`pending_event` 为空且无 active combat），除 `event/choose`、`combat/action`、存档读取外统一调用。

#### P1-6 禁地 Boss 胜利回调失败会卡死会话，且重试路径不清晰
- **位置**：`backend/app/services/combat_service.py:148-154`（先 `complete_forbidden`，后 `CombatSessionRepository.delete`）；`sect_bridge_service.py:525-563`
- **成因**：禁地奖励结算在删除会话之前执行。若 `ForbiddenLandService.enter()` 抛错（贡献不足、内容缺失、DB 异常），会话仍以 `victory` 状态残留。
- **影响**：`action_service.py:276-277` 因会话存在拒绝新行动；`combat_service._require_session` 又因状态非 `active` 抛 4014 → **玩家卡死**，且再次进入可能重复结算。
- **修复建议**：胜利后先把会话标记为 `settling` 或直接删除，再发奖；禁地回调失败进入补偿/重试队列，保证幂等。

#### P1-7 散修奇遇无次数/冷却限制，可无限刷贡献与功法
- **位置**：`backend/app/services/sect_bridge_service.py:397-425`
- **成因**：`sansxiu_encounter()` 只校验身份，未校验频率/年度次数/冷却，每次调用都会 `weighted_pick` 并累加 `general_contribution`。
- **影响**：可脚本化无限刷贡献（进而兑换功法/装备），经济与成长曲线被击穿。
- **修复建议**：增加 `encounter_last_days` 冷却或"每游戏年 N 次"配置；与禁地一致做年度计数。

#### P1-8 敌人逃跑仍按全胜发奖（经验/灵石/掉落）
- **位置**：`backend/app/domain/combat.py:439-445`（置 `enemy_fled=True` 且 `status=victory`）；`backend/app/services/combat_service.py:120-154`（未读取该标记）
- **成因**：领域层注释写"无掉落由 service 处理"，但 service 未实现。
- **影响**：把杂兵打到 20% 以下等它逃跑，可**零风险拿全额经验/灵石/掉落**。
- **修复建议**：`_after_victory` 检查 `session["flags"]["enemy_fled"]`，仅发经验（或减半），不发灵石/掉落；补用例。

### 2.5 "碰撞与物理"映射结论（战斗判定）

本项目无实时物理。对应的 `domain/combat.py` 实现质量整体良好：纯函数、`deepcopy` 不改入参、可 JSON 往返、RNG 按 `turn/actor/source` 分 stream、30 回合上限、破防三档、减伤上限 75%、逃跑 clamp 5%–90%。

发现的战斗相关问题：

- **P1-8**：逃跑敌人仍全额发奖（已列）。
- **P2-14（补充）**：防御指令的生效依赖出手顺序。`step()` 在回合开始把双方 `defending=False`（`:494-495`），若敌方先手，玩家本回合的 `defend` 在挨打之后才置位，**防御对先手敌人无效**。建议明确"防御持续到本回合结束/下一回合开始"的语义。
- **P2-15（补充）**：`combat_service.act()` 对 `item` 指令先扣道具（`:196`）再推进回合；若 `step()` 抛错（如配置/状态异常），道具已扣、回合未推进。建议先校验再扣，或放入同一事务。

## 4. 模块依赖与耦合分析

```
web(static/templates)
        │ fetch /api/v1
        ▼
api/game_router.py ── api/sect_router.py
        │
        ▼
services/*  ──────────────┐
   │        │              │
   │        ▼              ▼
   │   domain/*        db/game_repository.py
   │   (纯逻辑)         db/repository.py（既有宗门，权威）
   ▼                       │
content/* (冻结 YAML)      ▼
   │                   SQLite (game.sql → sect_contribution.sql)
   └── core/*（clock/rng/errors/response）
```

**观察**

1. `domain` 保持纯净（不 import db/fastapi），这是本项目最好的架构约束，应继续保持。
2. `services/sect_bridge_service.py` 是最大的耦合点（563 行）：既做身份校验、又做既有 Service 适配、又做奖励发放、还直连 SQL。建议拆分为 `identity_service` / `forbidden_service` / `exchange_facade` 三个小模块。
3. 事务边界跨越 `game_repository`（自动提交）与 `repository`（依赖调用方）两套风格，是 P1-1 的根因；建议先统一连接/事务抽象，再谈业务修复。
4. `stats_service` / `sect_bridge_service` 直接 `get_conn().execute` 聚合 SQL，绕过了 Repository；短期可接受，长期应下沉。
